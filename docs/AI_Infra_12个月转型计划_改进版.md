# 后端工程师转向 AI 推理平台的 12 个月执行计划

版本：2026 年 9 月。适用画像：在职、有多年后端或分布式系统经验，每周可稳定投入约 15 小时，希望转向模型服务、AI 平台或推理基础设施岗位。

## 先确定目标

12 个月的目标是拿出能供招聘方检查的工程证据，并争取完成岗位转换。个人实验能证明技术能力，但不能代替真实生产环境的运行经验。因此求职主线是 **AI 平台后端、模型服务平台、推理平台工程师**；GPU 性能、多卡通信和底层算子是根据岗位反馈选择的深化方向。不要把「高级 AI Infra」或「一年内成为 CUDA/NCCL 专家」设为硬结果。

全年只维护两类成果：

1. **一个旗舰仓库** `llm-inference-platform`，从单卡服务逐步加入网关、压测、观测、部署和故障演练。
2. **两份可复现技术报告**：一份推理服务容量与延迟报告；另一份针对真实瓶颈的优化或多卡扩展报告。报告保留配置、原始数据、分析脚本和失败实验。

已有后端或通信/专网业务经历如果能够公开描述，应作为第三类证据：说明你过去如何处理容量、可靠性、网络、交付或客户现场问题，再展示这些能力如何迁到推理平台。涉及公司数据时只使用获准公开的脱敏事实。

## 时间和预算规则

- 每周安排 **12 小时计划内工作 + 3 小时机动**。机动时间用于环境故障、重测、面试或休息，不预先排满。按 52 周计算，计划内约 624 小时，机动约 156 小时。
- 每月只验收一个主交付。可运行代码、原始数据和清楚的 README 优先于文章、视频和新框架。
- 连续两周低于计划进度时，缩小当月功能，不补加每日工作时长。月底未通过验收，下月第一周先修核心问题。
- GPU 费用按 **所选实例的实际小时价 × 预估小时数 + 存储/流量/失败重跑余量** 计算，并在租用当天核价。全年预算先设上限，不把旧报价当作当前价格。开卡前先在 CPU 或 mock 环境完成脚本冒烟，并设置自动停机。
- 24GB 单卡适合小模型或受控的 7B 实验；是否能服务较长上下文和高并发，要由权重、KV Cache、框架开销及实测容量决定。压测并发档位是**探索值**，不是必须全部无错误完成的承诺。

## 月度路线

每月计划内投入约 48–52 小时。表中的 GPU 时长是实验准备完成后的估计值，不能据此推导固定费用。

| 月份 | 唯一主目标 | 可检查的月底交付 | GPU 使用与边界 |
|---|---|---|---|
| M1 | 跑通并解释一次小模型推理 | `infer.py`、环境清单、CPU/GPU 正确计时、显存记录和请求链路图 | 以 CPU 为主；短租 GPU 约 4–8 小时。已有 PyTorch 基础可跳过重复课程 |
| M2 | 理解 prefill、decode 和 KV Cache | 最小 attention/KV Cache 实验；容量估算与原始数据；能解释公式假设 | 单卡约 8–12 小时；用小模型验证，不追求大参数量 |
| M3 | 建立可运行的单卡推理服务 | 旗舰仓库 V0：vLLM 服务、网关、流式转发、超时、健康检查、容器启动与测试 | 单卡约 12–18 小时；只选一种网关语言 |
| M4 | 做第一份可信的容量报告 | 固定模型、硬件、版本和请求分布，扫描到达率或并发，记录 TTFT、TPOT、吞吐、错误率、显存及原始数据 | 单卡约 15–25 小时；先测一个服务框架。SGLang A/B 只在时间充裕且环境可对齐时做 |
| M5 | 让服务故障可定位 | 网关与推理服务指标、一个 dashboard、两条有依据的告警、一次 OOM 或过载故障演练 | 集成时短租约 8–15 小时；不追求指标和告警数量 |
| M6 | 形成第一版可展示平台并开始试投 | V1：部署脚本或 Helm、CI、runbook、架构图、容量报告链接；陌生人在约 45 分钟内跑通核心路径 | 若租用环境支持 GPU/K8s，做一次真实 GPU Pod 冒烟。单节点只声称部署和恢复验证，不声称集群高可用 |
| M7 | 根据面试反馈选深化方向 | 写下目标岗位的高频缺口，并选择 **性能优化** 或 **分布式/算力平台** 一条支线；完成该支线的最小实验 | 开卡前先明确报告要回答的问题 |
| M8 | 完成一次诊断到改动的闭环 | 性能支线：Nsight/Triton 或服务参数优化。分布式支线：GPU 拓扑、TP/NCCL 基线。必须有正确性或结果一致性检查 | 单卡或双卡按支线短租；报告同时展示未改善的 shape/负载 |
| M9 | 交付第二份可复现报告 | 性能支线：端到端延迟或吞吐收益与边界。分布式支线：单卡/双卡比较和通信开销解释 | 双卡只在模型、脚本、数据准备好后集中租用；单卡方案也可过关 |
| M10 | 补足目标岗位的系统短板 | 按 JD 选择一项：NUMA/PCIe/网络诊断、GPU 调度与容量、或国产加速器适配；将结果接入平台文档 | 没有真实 RDMA 硬件时，明确标注概念理解与已验证实验的差别 |
| M11 | 获取外部代码或使用反馈 | 复现一个相关 issue 并提交有测试的上游 PR，或请同行试跑旗舰仓库并处理其反馈 | PR 合并受维护者和项目节奏影响，不能作为硬验收 |
| M12 | 稳定作品和完成求职冲刺 | V2 release、两份报告、简历中的三段项目证据、30 分钟架构讲解；持续投递与复盘 | 只为最终复测租卡；冻结功能，优先修复可复现性和文档 |

### M6 和 M9 的求职闸门

**M6：** 面向 AI 平台后端、模型服务、LLMOps/平台工程和企业私有化部署岗位试投。用面试记录区分「简历没进面试」和「面试技术缺口」，不要凭感觉加学习任务。目标是取得可用反馈，不以固定面试次数作为完成条件。

**M9：** 若 M6 已有平台岗位反馈且第二份报告完成，扩大到推理平台或算力平台岗位。只有在真实实验能讲清瓶颈、拓扑和边界时，才把 GPU 性能或分布式推理写进简历标题。

**M12：** 高级岗位可以挑战，但应以既有生产系统经验加上推理平台证据共同支撑。个人单节点平台和短时租卡实验，不应包装成多年 GPU 集群运维经历。

## 旗舰仓库的最小范围

```text
llm-inference-platform/
  README.md              # 问题、架构、运行方式、结果和限制
  gateway/               # 鉴权或限流、超时、流式转发、request_id
  serving/               # 锁定版本的服务配置
  deploy/                # compose；M6 再加 Helm 或部署脚本
  benchmark/             # 负载定义、运行脚本、原始数据、报告
  observability/         # dashboard、告警、故障记录
  docs/                  # 设计取舍、容量估算、runbook
  tests/                 # 网关测试、服务冒烟与关键故障路径
```

V1 必须先解决「别人能运行、能压测、能看到故障」三个问题。多模型路由、复杂灰度、自动扩容、speculative decoding 和大规模集群调度，只有目标岗位明确需要且现有平台稳定时才加入。单节点 Kubernetes 演示要写清它验证了什么，以及哪些生产性质尚未验证。

## 报告的最低证据标准

每次实验记录 `git_sha`、模型及版本、服务框架版本、GPU/驱动/CUDA、精度或量化、输入/输出长度分布、到达率或最大并发、运行时长、warm-up、重复次数与错误。保留请求级或运行级原始结果；报告至少给出 TTFT、TPOT、端到端延迟、吞吐、成功率和显存。P95/P99 必须附样本数，样本不足时不要作精确尾延迟结论。

公平比较须在同一硬件、模型、精度和负载下进行，并说明缓存开关和启动参数。端到端结果与单个 kernel 的 microbenchmark 分开陈述。优化未带来收益也可成为合格报告，只要 profile 支持瓶颈判断、实验可复现、结论边界明确。

## 每月验收与调整

月底只问四件事：

1. 陌生人能否按 README 运行本月主交付？
2. 结论能否由保存的配置和原始数据重新计算？
3. 我能否讲清一次失败、瓶颈或设计取舍？
4. 本月面试或目标 JD 的反馈，要求下月保留、修改还是删掉什么？

前三项任一项不成立，先修核心证据；文章、视频、新框架和额外 GPU 实验全部后移。每季度预留一周处理积压与求职，不新开主题。

## 第一个七天

| 天 | 任务 | 可见结果 |
|---|---|---|
| 1 | 整理 15–20 个目标岗位 JD，标出已有经验与真实缺口；建立旗舰仓库 | 岗位矩阵和首次提交 |
| 2–3 | 用 PyTorch 跑通张量、dtype、device 和正确计时 | `timing.py` 与原始 CSV |
| 4–5 | 跑通小模型推理，记录内存与一次请求链路 | `infer.py`、环境清单、请求链路图 |
| 6 | 在新环境复现；补依赖锁定和错误说明 | README Quickstart |
| 7 | 用 15 分钟讲解实验，并删掉下周不需要的学习项 | 一页复盘 |
